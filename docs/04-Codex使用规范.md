# Codex 使用规范

## 1. 权限策略

仓库默认采用：

```toml
approval_policy = "on-request"
sandbox_mode = "workspace-write"
```

含义：Codex 可在工作区内读取、编辑和执行常规命令；访问网络、工作区外文件或跨越沙箱边界时应触发审批。

以下操作必须人工确认：

- 安装或升级生产依赖。
- 删除大量文件或用户数据。
- 写工作区外路径。
- 访问云模型、外部 API 或下载二进制工具。
- Git push、发布、签名和上传制品。
- 修改安全策略、密钥、CI Secret 和自动更新渠道。

## 2. 提示词规则

有效任务应包含：

- 背景和用户问题。
- 明确目标与非目标。
- 相关文档和代码路径。
- 验收标准。
- 必须执行的测试命令。
- 输出格式。

避免：“把这个功能做完”“优化一下项目”“帮我全面重构”。

推荐：“读取 `docs/01-产品需求文档-MVP.md` 的 2.2，先分析现有文档模型和导入流程，给出不超过 8 步的计划。确认后实现 Markdown/TXT 导入；不处理 PDF/DOCX；补成功、重复文件和损坏编码测试；运行后端质量门禁并汇报结果。”

## 3. 计划与实现分离

以下任务先 Plan 后 Code：

- 影响数据库 Schema。
- 涉及三个以上模块。
- 引入新依赖或外部工具。
- 修改进程模型、任务状态或安全边界。
- 预估超过 2 小时。

计划中必须把每项验收标准映射到实现步骤和测试。

## 4. 并行代理规则

适合并行：

- 一个代理调研现有代码，一个代理设计测试矩阵。
- 后端 API 和前端纯展示层在契约稳定后并行。
- 文档补充和不冲突的测试补充。

不适合并行：

- 多代理同时修改同一迁移或核心领域模型。
- API 契约尚未确认时并行前后端实现。
- 同一 Bug 的多个代理各自修复并直接合并。

## 5. 结果审查

Codex 最终汇报至少包含：

1. 实际修改文件。
2. 行为变化。
3. 执行的命令及结果。
4. 未执行的验证及原因。
5. 迁移、兼容和安全影响。
6. 残余风险和下一步。

不得只汇报“已完成”“测试通过”而不给证据。
